1

RAG 是什么？一句话 + 一个类比

RAG = Retrieval-Augmented Generation（检索增强生成），中文可以理解为：「先查资料，再回答」。

大模型像一个「上知天文下知地理、但没看过你家文件的学霸」。RAG 做的事情是：你提问时，先从你的资料库里把最相关的几段内容检索出来，连同问题一起交给模型，让模型看着资料回答，并给出处。

🏛️ 图书馆类比：把「资料库」想成一座图书馆，把「大模型」想成一位聪明的同学。RAG 不是让他背下整座图书馆，而是：你提问 → 图书管理员火速找到最相关的几页 → 递给这位同学 → 他翻着这几页回答你，还告诉你出处。

🤔 为什么不能把整个知识库直接「喂」给模型？

原因说明
① 上下文窗口有限模型一次能「看」的文本量有上限，资料一多根本塞不下。
② 推理成本高输入按 token 计费，全量塞入会非常贵。
③ 推理速度慢输入越多，模型要「消化」的越多，回答越慢。
④ 知识与时效模型只学到训练截止前的知识，你的私域/最新资料它没学过，还可能一本正经地编造（幻觉）。

2

RAG 用在哪些场景？

核心规律：「资料是私有的 / 最新的 / 需要给依据的」，就适合 RAG。

🏢 企业知识库问答

员工手册、制度、产品文档太多，让员工直接问机器人，秒出答案并带出处。

🎧 智能客服

基于售后政策、FAQ、说明书回答用户问题，可引用具体条款。

⚖️ 法律 / 医疗 / 金融

法规、指南、研报等专业文档，要求答案「有依据、可追溯」。

📰 时效 / 实时信息

模型不知道今天的新政策，把最新新闻、公告、内部通知喂进知识库再问答。

🎓 学习与写作辅助

把课件、书籍、研究资料建成个人知识库，问它「这个概念在哪讲过」并引用原文。

📁 多格式文档问答

PDF / Word / Excel / 网页 / 扫描件（OCR）统一入库，跨文档提问。

4

五个环节，逐个拆解

第 1 步

分片 Chunking · 把长文档切成「好检索的小块」

一份资料可能有几十页、几万字。检索时我们只想拿「一小段最相关的」，所以先把文档切成一段段 chunk（内容块）。分块质量直接影响检索精度，是整个 RAG 的「地基」。

  • 固定长度 + 重叠（入门推荐）：按字符/词数切分，设置 chunk_size 与 chunk_overlap。起步建议：约 512 个 token 一块，重叠 10%–15%，再针对自己的数据调参。
  • 按文档结构切（进阶推荐）：以标题、段落、章节、表格为自然边界切分，语义更完整；结构化文档（Markdown / HTML / PDF 大纲）效果明显更好。
  • 语义分块：让模型按「意思完整」来分，更聪明但更慢、更贵。
  • 父子分块：建两层——小子块负责精准检索，其所属的大「父块」负责提供完整上下文，兼顾精度与上下文完整性（代价是索引体积约翻倍）。
📖 类比：把一本厚书拆成一页页可以单独查阅的卡片，每张结尾留一句与下一页重复的「衔接句」，这样无论从哪张卡片看起都不丢上下文。

⚠️ 口诀：切太大 → 召回太糙（一锅端、不精准）；切太碎 → 语义被切断（一句话拆两半，互相找不到）。chunk 应大到「装得下答案 + 局部上下文」，小到「top-k 命中不掺无关噪音」。

第 2 步

索引 Indexing · 给每块文本做「语义编号」并入库

索引做两件事：

  • ① 向量化（Embedding）：把每个 chunk 交给 embedding 模型，转成一串数字（如 768/1024/1536 维的向量）。规律是：语义越相近的文本，向量距离越近——「怎么退钱」和「退款流程」关键词不同，但向量很接近。常见模型：BGE、text-embedding 系列、通义/智谱等的向量模型。
  • ② 存入向量数据库：把「文本 + 向量 + 元数据」存进专门的向量库（Milvus、Qdrant、Chroma、FAISS、pgvector 等）并建好索引，让「大海捞针」变成「秒级查找」。
  • ③ 附上元数据：标题、作者、日期、页码、文档类型等，之后可用来过滤与溯源——这是「内容盲检索」升级为「上下文感知检索」的关键。
  • ④ 可叠加关键词索引：同时建立 BM25 关键词索引，为后面的混合检索做准备（专有名词、编号、缩写靠它更准）。
🏷️ 类比：给每张卡片写「内容简介 + 唯一编号」，按编号排好检索柜；再额外做一份「关键词目录」。之后无论按意思还是按词，都能快速找到卡片堆。
第 3 步

召回 Retrieval · 把问题变成向量，找出最像的 top-k 段

用户提问后，系统把问题用同一个 embedding 模型转成向量，再到向量库里找距离最近的若干个 chunk（top-k，一般 5–20）。

  • 召回是「粗筛」：追求「别漏掉对的」，允许夹带一些不太相关的。
  • 设相似度阈值过滤：太不像的直接丢弃，避免答非所问。
  • 召回不准怎么办？按顺序排查：分块策略 → embedding 模型 → 混合检索（向量 + BM25）→ 元数据过滤 → 查询改写 → 最后用重排兜底。
  • 进阶：查询改写——问题太模糊时，先让模型把问题改写好再检索：拆成多个子问题（多路查询）、生成一段「假设答案」去检索（HyDE）、或把问题抽象一步（Step-Back）。
🔦 类比：拿着问题去检索柜「海选」，先把最像的几十张卡片抱出来——此时不求精，只要「该在的都在」。
第 4 步

重排 Rerank · 逐条精读，二次排序

向量检索快但偏「近似」，排序不一定准。于是引入专门的 reranker（重排模型，通常是 cross-encoder）：把「问题 + 每一段候选」成对送进去精读打分，重新排序，只把最相关的前几名（如前 3 名）交给大模型。

  • 典型组合：召回粗筛（快、广）+ 重排精排（慢、准），又快又准。
  • 如果用了多路检索（向量 + 关键词 + 元数据过滤），可以先用 RRF（倒数排名融合）把几份结果合并，再统一重排。
  • 效果：明显减少「搜到了但排错位」导致的答非所问。
🕵️ 类比：海选抱回几十张卡片后，再请一位「细心的审核员」逐张精读、重新排队，只把最靠谱的 3–5 张递给学霸。
第 5 步

生成 Generation · 大模型「看着资料」作答

最后把 ①精选片段 + ②用户问题 + ③系统指令 拼成一段 prompt 交给大模型。指令通常要求：只依据提供的资料回答；资料里没有就老实说「不知道 / 资料中没有」；必要时标注答案来自哪一段（引用出处）。

  • 片段太多反而更差：只留最相关的前几名，控制喂给模型的上下文。
  • 对回答做「忠实度」校验：答案里的关键事实是否都能在检索片段里找到，找不到就降级或拒答。
✍️ 类比：超级学霸只允许看你递给它的几张卡片——不准开卷背别的书。这样答得「有依据、可溯源」，几乎不会胡编。
5

进阶优化：把 RAG 从「能用」做到「好用」

基础链路跑通后，效果不好大多是「检索不准」。下面按业界常见做法，从高性价比到进阶排序：

🔀 混合检索 + RRF 融合

向量检索（懂语义）+ BM25 关键词检索（精确词/编号）各查一遍，用 RRF 合并排序，通常立竿见影。

✍️ 查询改写

先让模型把口语化/指代不清的问题改写成检索友好的形式；进阶玩法：多路查询、HyDE、Step-Back。

⚖️ 重排精排

向量粗筛的排序不可靠，用 cross-encoder 精读打分再排序，只留前几名，性价比很高。

🌲 父子分块

小子块精准命中 + 父块补全上下文，专治「查到一句话却少了背景」的问题。

🏷️ 元数据过滤与权限

先按部门/文档类型/日期筛一遍再检索；同时是落地权限控制（谁能看到哪份资料）的基础。

🧹 清洗、压缩与缓存

入库前清理噪音/重复；对召回片段做上下文压缩；高频问题做语义缓存，省钱又提速。

🔧 效果不好时，按这个顺序排查

  1. 数据问题：文档有没有清洗？是不是有大量重复/OCR 乱码/扫描件没转好？
  2. 分块问题：512 token 起步调过了吗？有没有按文档结构切？切碎/切大各试一轮。
  3. 检索问题：embedding 模型是否匹配你的语言/领域？有没有试混合检索 + 重排？top-k 与阈值是否合适？
  4. 问题理解问题：模糊问题要不要先做查询改写？
  5. 生成问题：prompt 是否要求「只依据资料 + 给出来源」？片段是不是塞太多？
  6. 评估问题：有没有一组带标准答案的评测题？没有评测，优化就是在「盲调」。
6

效果评估：RAGAS 四大指标 + 常见坑

「感觉变好了」不算数。建议准备 30–50 条带标准答案的测试题，用开源评估框架 RAGAS 自动打分，量化每次改动。

📐 RAGAS 核心指标

指标衡量什么一句话理解
Faithfulness（忠实度）答案是否都「有据可依」答案里的每句话，检索片段里能找到依据吗？
Answer Relevancy（答案相关性）答案是否答到点子上答非所问、绕圈子 → 得分低。
Context Precision（上下文精确率）检索回来的片段是否精准相关片段是不是排在前面、无关的是不是混进来了。
Context Recall（上下文召回率）该检索到的有没有漏标准答案所需信息，是否都从知识库找回来了。

前两个指标盯「答得好不好」，后两个盯「检得准不准」——哪个低，就去优化对应环节。

⚠️ 新手最容易踩的 7 个坑

🗑️ 文档不清洗直接入库（乱码、广告、重复内容全进索引）
✂️ 所有文档用同一套分块参数，不管格式
🔍 只做纯向量检索，专有名词/编号永远搜不准
📏 不设相似度阈值，乱七八糟的片段也塞给模型
🧪 没有评测集，全凭「感觉」调参
🕰️ 知识更新后忘记重建索引，答案永远是旧的
🔐 忽略权限，检索层没有隔离机密文档
7

常见问题 Q&A

Q为什么不能把全部资料一次性「喂」给模型，非要检索？

四个原因：① 上下文窗口有限——模型一次能处理的文本量有上限；② 贵——输入按 token 计费，全量塞入成本爆炸；③ 慢——输入越多推理越慢；④ 不解决问题——私域、最新的知识模型本来就没学过，硬塞也答不对。RAG 每次只喂「最相关的那几小段」，省、快、还更准。

Q什么时候用 RAG，什么时候用微调？

一句话判断：问题出在「知识」→ 用 RAG；问题出在「行为」→ 用微调。

知识问题：缺事实、资料常更新、需要出处、知识库很大 → RAG 更合适。
行为问题：输出格式/语气/风格不稳定、需要模型学会固定套路 → 微调更合适。
生产环境最常用的是两者结合：微调保证风格稳定，RAG 提供最新、可溯源的领域知识。

Q有了 MCP + 搜索引擎 / 数据库，还需要 RAG 吗？

它们是不同层级的工具，可以组合而非二选一：

① 搜索引擎靠关键词，搜「怎么退钱」不一定找得到写「退款流程」的文档；向量检索靠语义，能理解意思相近的说法。
② 搜索引擎只能搜公网；公司制度、个人笔记等私有资料网上搜不到，必须放进自己的向量库。
③ MCP 是「给模型接上工具的手」，它完全可以把「调向量库检索」也做成一个工具。成熟的系统通常是：搜索 API 查实时信息 + 向量库查私域资料 + SQL 查结构化数据（多路召回）。

Q让 RAG 全量梳理几千条新闻，为什么经常漏内容？

因为 RAG 擅长的是「模糊检索 → 找到精准小片段」，它天生不适合「把全量数据穷举一遍再归纳」的任务。

如果任务是「把几千条记录全部读完再总结趋势」，应该改用：分批喂给模型再汇总（Map-Reduce 式），或 MCP + 数据库做结构化统计。先分清任务类型，工具才不会用错。

Q怎么系统性地降低幻觉、提高质量？

按链路逐个加固：

① 数据：来源要权威、入库前清洗去重；
② 检索：分块、embedding、混合检索、重排、阈值过滤，别让无关内容混进 prompt；
③ 指令：prompt 写死「只依据资料回答，没有就说没有，并给出来源」；
④ 校验：对答案做忠实度检查，关键事实在片段里找不到就拒答或降级；
⑤ 评测：用 RAGAS 等框架持续打分，每次改动都能量化好坏。

零基础术语表（遇到就查，还能用闪卡背）

正文中带虚线下划线的术语都可以悬停/点击看解释；下方闪卡可帮你把词背下来。

RAG（检索增强生成）Retrieval-Augmented Generation：先检索资料，再让大模型基于资料生成回答的技术。
大模型 / LLMLarge Language Model：如 GPT、DeepSeek、Qwen 等，能理解和生成自然语言的模型。
上下文窗口模型一次对话能「看」的最大文本量，单位是 token；超出上限的内容无法处理。
Token（词元）模型处理文本的最小单位；中文约 1 个汉字 ≈ 1–2 个 token，也是计费单位。
Embedding（向量化）把一段文本变成一串数字（向量），语义相近的文本向量也相近。
向量数据库专门存「文本 + 向量」并支持按相似度快速检索的数据库。
Chunk（分块）把长文档切成的小段文本，是检索与喂给模型的基本单位。
父子分块分层策略：小「子块」用于精准检索，其所属的大「父块」提供完整上下文。
top-k召回时取相似度最高的 k 个片段；k 越大信息越多，噪音也可能越多。
余弦相似度衡量两个向量方向接近程度，常用作文本相似度，越接近 1 越相似。
召回（Retrieval）根据问题从知识库中找出候选相关片段的过程。
重排（Rerank）用重排模型对候选片段「精读打分、重新排序」，留下最相关的前几名。
混合检索向量语义检索 + 关键词检索（如 BM25）结合，兼顾「懂意思」与「精确匹配」。
BM25经典的关键词相关度算法，适合精确词、编号、专有名词匹配。
RRF（倒数排名融合）Reciprocal Rank Fusion：把多路检索结果按排名加权合并成一份结果。
查询改写（Query Rewriting）让模型把模糊问题改写成更适合检索的形式，如多路查询、HyDE、Step-Back。
HyDEHypothetical Document Embeddings：先让模型写一段「假设答案」，再拿它去检索，提高命中率。
Prompt（提示词）写给模型的指令文本；RAG 中常包含系统指令 + 检索片段 + 用户问题。
幻觉（Hallucination）模型一本正经地编造不存在的答案；RAG 可显著缓解但不能根除。
元数据（Metadata）附着在文档/片段上的描述信息（标题、作者、日期、页码），用于过滤与溯源。
微调（Fine-tuning）用特定数据继续训练模型以改变风格/行为；解决「行为」问题，与 RAG 互补。
RAGAS开源 RAG 评估框架，用忠实度、答案相关性、上下文精确率/召回率等指标打分。
MCPModel Context Protocol：让大模型连接外部工具/数据（数据库、搜索引擎等）的开放协议。

动手实践：从「看懂」到「能搭」

🧭 零基础学习路线

  1. 吃透概念（本页）

    把「分片 → 索引 → 召回 → 重排 → 生成」五步在纸上画一遍，能给别人讲明白才算懂。

  2. 先用低代码平台跑通

    在 Dify / Coze 等可视化平台上传几份自己的文档，自动完成分块 + 向量化，直接对话体验全流程。

  3. 再上手代码框架

    用 LangChain 或 LlamaIndex（Python）写一个几十行的 RAG demo：加载文档 → 分块 → embedding → 向量库 → 检索 → 生成。

  4. 做效果评估

    准备 30–50 条带标准答案的测试题，用 RAGAS 打分，然后逐项优化（混合检索 → 重排 → 查询改写）。

  5. 走向生产

    考虑：权限与安全、索引更新机制、缓存降本、日志与可观测，再进阶尝试 Agentic RAG。
